# Beacon AR EF Core Power Tools — Review Feedback

## Findings

### High — Generated entity/view mapping cannot be resolved by the application host

- **Evidence:** generated methods resolve both a concrete mapper and view from DI (`src/BeaconAr.Domain/Receivables/Entities/Product.cs:57,65-66`; owning template `src/BeaconAr.Data/CodeTemplates/EFCore/EntityType.t4:257,266`), but the host registers only repositories and Providers (`src/BeaconAr.WebApi/Program.cs:163-164`). It never calls `RegisterMappers` or `RegisterEntities`. The required DMS reference registers both.
- **Consequence:** `Product.MapFrom`, `Product.MapTo`, and the equivalent methods for all nine entity/view pairs throw `InvalidOperationException` as soon as an official edit Provider or another caller uses them. The compile-time contract tests do not exercise this runtime path.
- **Smallest safe correction:** explicitly register generated mappers and `EntityBase` types from the Domain assembly in `Program.cs`, using the framework discovery extensions and an explicit assembly root. Add a focused DI test that resolves an entity, its view, and mapper and successfully executes both `MapFrom` and `MapTo`. Do not work around this with per-type manual registrations.

### High — The generated interface mapper accepts system-owned audit values from a view

- **Evidence:** `EntityInterfaceGenerator.cs:73-78` includes every declared scalar, including `CreationDate`, `CreatedByUserId`, `ModificationDate`, and `ModifiedByUserId`; the empty generated mapper delegates interface-to-entity mapping to `MapFromInterface` (`EntityType.t4:257,312`). The installed `EntityMapperBase` implements this as unrestricted Mapster adaptation. In contrast, the required DMS reference deliberately excludes its four standard audit properties (`Microsoft.DemoManagementSystem.Interfaces/EntityInterfaceGenerator.cs:18,129-133`).
- **Consequence:** once the requested official edit Providers/controllers adopt these generated views, a request can overwrite creation audit fields on an existing entity. `DbContextBase` stamps modification fields on update but does not restore creation fields, so this is not neutralized at save time. The current custom Providers do not call the generated mapper, which is why existing tests remain green.
- **Smallest safe correction:** retain the getter-only shared interface/type-nullability contract, but configure the generated mapper in the owning T4 to ignore server-owned audit fields on interface-to-entity mapping (or exclude those fields from the write mapping contract if the requirement is clarified that way). Add a mapper test proving an update cannot change creation audit values while ordinary editable fields map. Record the treatment of row-version, deletion, and snapshot fields in `decisions.md` before official Provider adoption; do not hand-edit generated classes.

### Medium — PE3101 cannot recognize the EFPT source header during assembly validation

- **Verified header:** all 28 generated Domain files and the generated context have the exact first line `// <auto-generated> This file has been auto generated by EF Core Power Tools. </auto-generated>`. The source-based `paradigm checks` implementation recognizes `<auto-generated` in the first 2,048 characters, and targeted Domain/Data checks pass.
- **Root cause:** `paradigm validate` analyzes restored assembly metadata, where comments do not exist. `EntitySetterRule.cs:17,21,32` suppresses PE3101 only for `GeneratedCodeAttribute` or `CompilerGeneratedAttribute`; the T4 emits neither (`EntityType.t4:142,320`). The resulting PE3101 flood is therefore deterministic and is not evidence that the EFPT header is malformed.
- **Consequence:** the task cannot end with a clean, truthful framework validation result, and genuine handwritten-setter warnings are buried among generated persistence warnings.
- **Smallest safe correction:** preserve the exact first-line EFPT ownership marker and make the owning T4 decorate generated types with `System.CodeDom.Compiler.GeneratedCodeAttribute`; regenerate instead of editing output. No heuristic namespace/base-type exception should be added to PE3101. Add an application fixture asserting a generated entity carries the compiled attribute and that `paradigm validate` no longer reports it. The existing CLI rule already recognizes this attribute.
- **Guidance learning:** update the database-first/setup/review skills to require both a source ownership marker (for source checks and replacement tools) and a compiled generated-code attribute when assembly-based validation is part of acceptance. This is a deterministic rule suitable for a fixture, not a suppression or a judgment-only exception.

### Medium — Regeneration does not enforce its declared exact output boundary

- **Evidence:** `build/regenerate-persistence.ps1:59-65` accepts any 28 top-level `.cs` files carrying the marker; it does not validate the exact expected filenames, reject other files, or verify the current owned files before invoking a mutating generator. EFPT also creates ignored `src/BeaconAr.Data/efcpt-readme.md` outside the two documented generated boundaries (`.gitignore:4`; `decisions.md:24`). A failed EFPT invocation can leave partially replaced output before the script detects error text. The manifest still restores the unused legacy `dotnet-ef` tool (`.config/dotnet-tools.json:12-15`).
- **Consequence:** a missing selected object can be masked by a stale/different generated file, accidental output is silently retained, and a failed run is not non-destructive/atomic. Retaining `dotnet-ef` also contradicts the stated replacement of the legacy workflow.
- **Smallest safe correction:** define the exact 28 entity/view filenames plus the context and verify that set, the exact markers, and absence of unexpected files both before and after generation. Resolve the unavoidable EFPT readme explicitly—prefer a supported suppression/staging layout; if none exists in 10.1.1386, remove only that known tool byproduct after verifying its identity and document the exception. Remove `dotnet-ef` from the example-local manifest after confirming no remaining consumer. Add a failure-path test or dry-run/staging check proving source output is unchanged when generation fails.

### Low — The scalar-contract test can pass with an incomplete generated interface

- **Evidence:** `LayerBoundaryTests.cs:299-313` iterates only properties that already exist on `TContract`. It checks entity/view CLR types and compares entity nullability with view nullability, but it does not compare the interface's nullability, assert getter-only access, or prove that every intended entity scalar appears in the interface.
- **Consequence:** a generator regression that silently drops one scalar—or emits the wrong nullable annotation on the interface—can leave this test green, weakening the compile-time mapping guarantee requested by the task.
- **Smallest safe correction:** compare the exact expected declared scalar-property set across entity, interface, and view; assert every interface property has a getter and no setter; compare `NullabilityInfoContext` read state for all three surfaces. Keep the nine generic assignability assertions.

### High — The failure-recovery test mutates the checked-in generated source tree

- **Evidence:** every Architecture test run launches the production regeneration script (`tests/BeaconAr.Architecture.Tests/GeneratedMappingTests.cs:131-145`). Its `-TestFailureRecovery` path first removes the real ignored EFPT readme and then appends to the checked-in `Product.cs` and creates `Unexpected.cs` in the checked-in generated directory (`build/regenerate-persistence.ps1:213,215,220-223`). It normally restores those files, but the mutation happens before the recovery assertion.
- **Consequence:** killing the test process, a host crash, or a concurrent build/test observing the fixture window can leave or consume corrupted source. A test run should not transiently rewrite repository sources, and the current test is unsafe under parallel CI or IDE test execution even though the normal-path fixture passed locally.
- **Smallest safe correction:** parameterize the boundary/backup helpers or extract the pure boundary-restore behavior, copy the 29-file fixture into a uniquely named temporary directory, and perform intentional mutation/recovery only there. Keep a production-script check that the real paths are resolved and validated, but never damage them to prove rollback. Validate and remove the temporary root with the same path guards in `finally`.

### Medium — The runtime registration test does not exercise the actual Web API host and relies on an indirect dependency

- **Evidence:** `DomainAssemblyRegistrationResolvesAndExecutesGeneratedMapping` constructs a fresh `ServiceCollection` and repeats the two registrations itself (`GeneratedMappingTests.cs:16-18,157-163`). It remains green if the real registrations at `src/BeaconAr.WebApi/Program.cs:166-167` are deleted. To access `Paradigm.Enterprise.WebApi.Extensions`, the Architecture test project adds a reference to the application entry project (`BeaconAr.Architecture.Tests.csproj:9`) instead of referencing the package from the project that uses its types; the setup skill explicitly rejects accidental transitive package access.
- **Consequence:** the claimed host regression test does not guard the host, and a low-level Architecture suite now restores the complete Web API dependency graph solely to call two extension methods.
- **Smallest safe correction:** place the host-resolution assertion in `BeaconAr.WebApi.Tests`, which already owns the API host dependency, and resolve `Product`, `ProductView`, and `ProductMapper` from the actual configured application services. Keep mapper behavior/metadata tests at the Domain or Architecture boundary without importing the Web API project. Remove the new Architecture-to-WebApi project reference and refresh its lock file in locked mode.

### Medium — The generation error path can disclose the connection string

- **Evidence:** the script creates a redacted full log at `build/regenerate-persistence.ps1:262-263`, but builds `$safeErrors` from the original unredacted `$generationLog` and inserts it into the thrown exception at lines 265-266.
- **Consequence:** if EFPT includes its positional connection argument in an error/exception line, a password-bearing connection string is written to test/CI/terminal error output despite the documented credential-free workflow.
- **Smallest safe correction:** derive the thrown excerpt from the already redacted log, or redact the excerpt before constructing the exception. Add a script-level fixture with a sentinel password in simulated EFPT output and assert that neither stdout nor stderr contains the sentinel.
