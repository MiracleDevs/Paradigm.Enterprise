# Beacon AR Web API implementation decisions

## Secure controller base exception

The installed Paradigm `ApiControllerBase`, `ReadApiControllerBase`, and `EditApiControllerBase` types inherit `[AllowAnonymous]`. ASP.NET Core treats that metadata as authoritative; adding `[Authorize]` or a fallback policy to a derived controller does not restore bearer authorization. The generic mutation actions also accept whole generated views and do not express Beacon AR's distinct create/update payloads, ETags, idempotency, audit, and lifecycle rules.

For this protected public API, the business controllers therefore remain direct `ControllerBase` types with explicit read/write policies. This is a deliberate security exception, not a replacement framework abstraction. The Providers do use the official `EditProviderBase`, and their generic `SaveAsync`/`DeleteAsync` paths remain fail-closed so callers cannot bypass the application-specific mutation workflows.

## Generated views and transport compatibility

The generated `*View` types are the actual response and pagination item types for master-data endpoints. They include joined display values such as user display names and, for customer addresses, customer and address-type display data.

Existing clients already consume `version`, `type`, `defaultBilling`, and `defaultShipping`. The database-generated property names are `RowVersion`, `AddressTypeCode`, `IsDefaultBilling`, and `IsDefaultShipping`. A source-generated JSON contract modifier aliases those properties at the HTTP boundary. This keeps compile-time view/entity interface validation and generated ownership without imposing an avoidable breaking wire-format change.

Legacy DTO-returning Provider methods are retained as compatibility adapters and delegate to the generated-view methods. This avoids duplicating repository access or mutation behavior; all mapping remains in the Provider layer.

## Microsoft Identity Web authorization behavior

`Microsoft.Identity.Web` normally rejects access tokens that contain neither `scp` nor `roles`. Beacon AR needs such a valid authenticated token to reach its own exact permission policy and receive `403`. `AzureAd:AllowWebApiToBeAuthorizedByACL` is therefore enabled, while `PermissionEvaluator` remains the sole exact, case-sensitive interpreter of the configured grants. Testing adds a static symmetric signing configuration only after startup has confirmed the environment is exactly `Testing`.

Release one is delegated-user-only and assumes a Microsoft Entra v2 access token issued for the Beacon AR API audience; ID tokens are never accepted as API credentials. Microsoft Identity Web owns signature, issuer, tenant, audience, and lifetime validation. An ASP.NET Core authorization requirement then runs before `CurrentUserMiddleware` and requires non-empty `oid` and `sub` identity inputs. It does not compare them to classify the actor. If `idtyp` is present, only `user` is accepted; `app` and unknown values are forbidden. If `idtyp` is absent, a non-empty `scp` claim is required to establish a delegated token, so roles-only and no-scope token shapes are forbidden before user resolution. Tokens containing both `scp` and `roles` are delegated users, and exact roles assigned to that user remain eligible for permission evaluation. Application-only callers are not supported because Beacon AR has no service-principal audit actor; adding them requires a separate identity and audit model.

## Documentation exposure and artifact generation

Swashbuckle middleware runs before authentication only inside the Development branch, making `/openapi/v1.json`, `/swagger`, and Swagger static assets intentionally anonymous there. The branch is not registered in Testing or production. The public contract is instead kept as a checked artifact generated by the isolated PowerShell helper; runtime production documentation exposure is not required to publish the artifact.

## Root metadata

The anonymous root exposes only the stable application name and the Web API assembly informational version with build metadata removed. It does not return environment, tenant, connection, authentication, or health configuration. Readiness and liveness retain their separate endpoints and semantics.

## Semantic-check scope

`paradigm checks run --project BeaconAr.slnx` cannot resolve Aspire's generated `Projects` namespace in `BeaconAr.AppHost`, even though the full Release solution build succeeds. The deterministic checks are therefore also run directly against `BeaconAr.WebApi`, `BeaconAr.Providers`, and `BeaconAr.Domain`, where all checks pass. `paradigm validate` succeeds against the complete solution. This is a semantic-tool/Aspire design-time limitation, not a Web API compilation failure.
